Community Evidence Review

This local app helps a founder examine supplied material from one public community against one consumer problem. It keeps original evidence visible, separates AI-assisted observations and interpretations from unknowns, and leaves the final judgment to the founder.

The browser keeps the active review in page memory. The user can explicitly download a text snapshot; the app itself does not save, manage, or reopen reviews.

One normal review, from start to result

  1. FounderEnters a problem, community, and supplied source items.
  2. Browser workspaceChecks fields and sends a valid submission.
  3. Local API routeReceives the request inside this Next.js app.
  4. Validation and orchestrationChecks input, then checks result shape and source IDs.
  5. OpenAI Responses APIAnalyzes only the supplied material; no search tools are provided.
  6. Validated reviewStructured findings and unknowns return through the local route.
  7. Browser reviewShows original supplied evidence separately from AI-assisted findings.
  8. Founder judgmentThe founder may select, replace, or clear their own judgment.
  9. Optional local text file“Download results” creates a snapshot only after the user clicks.

The browser sends review material to the local server route for analysis. The server-only provider module reads the OpenAI key, so the key never enters browser code. Founder judgment is UI-only and is not included in the analysis request. “Download results” creates community-evidence-review.txt only after a click; without a selected judgment, the file says “No founder judgment selected.”

The browser/client is the page and code running on the user's device. The server is the local app code that receives the analysis request and protects the provider key. The browser keeps form, review, and judgment in React state (temporary page memory); a refresh starts a new page state. The download is a user-made file, not saved-review storage managed by the app.

Separate path: no supplied source evidence

Founder continues without source material → the browser shows Evidence review unavailable → no API/provider request is made → no founder judgment is offered.

The workspace has an early no-source check, and the analysis service also returns an unavailable status before calling the provider if it receives an empty source list.

A short code route

Reference route based on the current source. This map does not claim that a reader has completed an interactive editor tour.

  1. Browser entry and result: components/review-workspace.tsx — handleSubmit validates before submission; submitAnalysis sends a request and displays its result. React state holds the active page data, so refreshing clears it. The same component keeps judgment local and builds the optional download in the browser.
  2. Server doorway and checks: app/api/analyze/route.ts — POST reads the submitted JSON and maps errors to safe HTTP responses. lib/evidence-analysis.ts — analyzeEvidence validates the request, bypasses the provider for no sources, and checks analysis structure and cited IDs before returning a review.
  3. Allowed shapes and provider: lib/contracts.ts defines the accepted fields and structured result; lib/openai-analysis.ts — analyzeWithOpenAI makes the server-side provider request and returns parsed structured output. Its API key is read only on the server.

“Structured output” means the model response must fit a predefined shape—claims and unknowns with specific fields—rather than an unrestricted paragraph. Runtime validation checks that shape and confirms claims refer only to submitted source IDs; it does not prove that an interpretation is correct.

The OpenAI request uses store: false to disable Responses API application state storage. This is not the same as disabling provider abuse-monitoring retention.

To change this, start here

  • Visible interface and browser flow: components/review-workspace.tsx
  • Request and response rules: lib/contracts.ts, then app/api/analyze/route.ts
  • Fictional example: lib/demo-fixture.ts
  • OpenAI model, instructions, and request settings: lib/openai-analysis.ts
  • Evidence orchestration and source-ID checks: lib/evidence-analysis.ts

A practice to reuse

Start from a boundary requirement, connect it to the code path, then verify the effect at the nearest testable boundary. Here, the requirement is “no supplied sources means no provider call.” handleSubmit in components/review-workspace.tsx shows the unavailable state before sending a request; analyzeEvidence in lib/evidence-analysis.ts also returns before invoking its provider for an empty source list. The test “does not call the provider when there are no source items” in tests/evidence-analysis.test.ts checks that boundary with a fake provider. This same requirement → implementation → test path can help make another project’s important limits concrete.
